## はじめに

サーバーのログファイルが大量に生成され、ディスク容量（ルートディレクトリ）が不足してしまった結果、サーバーリソースが足りず画像アップロード等の処理に失敗するケースがあります。

今回は、その際の現状確認から、応急処置、そして根本原因である `logrotate` の設定見直しまでの流れをまとめます。

## 現状の確認（ディスク容量・ログサイズ）

まずは `df` コマンドでディスクの使用状況を確認し、どこに問題があるか特定します。

```bash
$ df -h
ファイルシス   サイズ  使用  残り 使用% マウント位置
devtmpfs         983M     0  983M    0% /dev
tmpfs            998M     0  998M    0% /dev/shm
tmpfs            998M  109M  890M   11% /run
tmpfs            998M     0  998M    0% /sys/fs/cgroup
/dev/xvda1        20G   20G   20K  100% /
/dev/xvdg         79G   17G   59G   23% /var/www
tmpfs            200M     0  200M    0% /run/user/1000
```

`/dev/xvda1 (/)` が 100% となっており、ルート領域が完全に埋まっていることがわかります。一方で `/var/www` などには余裕があるため、システムログ等が怪しいと推測できます。

### 詳細な調査

どのディレクトリが容量を消費しているか、`du` コマンドで深掘りします。

```bash
$ sudo du -xh / | sort -rh | head -10
20G	/
19G	/var
18G	/var/log
17G	/var/log/nginx
1.3G	/usr
928M	/var/cache
926M	/var/cache/yum/x86_64/2017.12
926M	/var/cache/yum/x86_64
926M	/var/cache/yum
919M	/var/cache/yum/x86_64/2017.12/amzn2-core
```

調査の結果、`17G /var/log/nginx` と、Nginx のログが肥大化していることが特定できました。

## 応急処置（ログの切り詰め）

まずはサービスを正常化させるために、ディスク容量を空けます。

:::message alert
**注意**
稼働中のプロセスがファイルを掴んでいる場合、`rm` で削除してもディスク容量が解放されない（プロセス終了まで inode が残る）ことがあります。また、ファイル自体を消すと Nginx がエラーを吐く場合があるため、**削除ではなく「空にする（切り詰め）」**のが安全です。
:::

```bash
$ sudo ls -lh /var/log/nginx
# 巨大な access.log 等を確認

# truncate コマンドでファイルサイズを 0 にする
$ sudo truncate -s 0 /var/log/nginx/access.log
$ sudo truncate -s 0 /var/log/nginx/error.log
```

これでひとまずディスク容量が確保され、サービスの動作が復旧するはずです。

## 根本解決：logrotate の設定見直し

ログが肥大化した原因は、`logrotate` が正しく動作していないか、設定が不適切である可能性が高いです。

### 設定の確認

現在の `logrotate` の設定と動作をテストします。

```bash
# 設定ファイルの確認
$ cat /etc/logrotate.d/nginx

# デバッグモードでの実行テスト（実際には回転させない）
$ sudo logrotate -d /etc/logrotate.d/nginx
```

### 設定ファイルの更新

ログが適切にローテーションされるよう、`/etc/logrotate.d/nginx` を以下のように修正します。

```bash
$ sudo vi /etc/logrotate.d/nginx
```

```conf
/var/log/nginx/*.log {
    # 保持設定
    daily          # 毎日ローテーション
    rotate 14      # 14世代分保持
    size 100M      # 100MBを超えたらローテーション

    # 圧縮・命名ルール
    dateext        # ファイル名に日付を付与
    compress       # 圧縮する
    delaycompress  # 次のローテーションサイクルまで圧縮を遅らせる

    # その他
    missingok      # ログファイルがなくてもエラーにしない
    notifempty     # ログが空ならローテーションしない
    create 0640 app-user adm
    su app-user adm

    sharedscripts
    postrotate
        /bin/systemctl reload nginx > /dev/null 2>&1 || true
    endscript
}
```

## 設定後の動作確認

設定から数日後、ログが適切に分割・圧縮されているか確認します。

```bash
$ sudo ls -al /var/log/nginx
合計 380600
drwx------  2 app-user adm       4096  3月  1 03:11 .
drwxr-xr-x 10 root     root      8192  3月  2 03:09 ..
-rw-r-----  1 app-user adm   44845950  3月  2 13:49 access.log
-rw-r-----  1 app-user adm        568  2月 17 14:49 access.log-20260217.gz
-rw-r-----  1 app-user adm   71557231  3月  2 13:49 error.log
-rw-r-----  1 app-user adm        980  2月 17 14:49 error.log-20260217.gz
...
```

上記のように、日付付きの `.gz` ファイルが生成されていれば、正しく `logrotate` が機能しています。これでディスク容量不足によるトラブルを未然に防げるようになりました。
